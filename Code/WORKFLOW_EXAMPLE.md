# Example conversation: CSV report export

This illustrates one feature request going through the workflow. **AI** creates
analysis and drafts, and can explore the product's pinned Git commit by listing,
searching, and opening files on demand; it is not given a preloaded source-file
list or corpus in its prompt. **People** review and decide. The test client
carries requests and decisions between workflow stages.

```text
Requester:
  Add CSV export for reports.

Test client:
  Product registered (or reused). Feature request submitted.

AI business analyst:
  Draft specification: authorized users can export the current report and its
  selected filters as CSV. Open questions: which roles are authorized, and how
  should empty reports be handled?

Human reviewer:
  Please clarify the allowed roles and specify that an empty report exports
  with headers only.

AI business analyst:
  Updated the specification with those requirements.

Human reviewer:
  Approve specification.

AI architect:
  Analyzed the approved specification and repository. Reports are generated by
  the reporting component. The proposal is to add CSV formatting there; risks
  include large exports and escaping cell values.

Human reviewer:
  Approve architecture analysis.

AI developer skills:
  Independently reviewed implementation concerns. Their findings cover CSV
  escaping, filter preservation, empty-report behavior, and tests.

AI collaboration synthesis:
  Compared the developer findings, noted where they agree or conflict, and
  inspected relevant repository code when useful. It does not resolve
  disagreements or replace the original reviews.

AI planner:
  Drafted an implementation plan using all developer findings and the synthesis.

Human developers:
  Review the plan and request an export-size limit.

AI planner:
  Produces an updated plan for review.

Human developers and coordinator:
  Review the updated plan and approve it.

AI code generation:
  Works in a temporary checked-out feature branch based on the pinned commit.
  This stage alone can use all Copilot SDK built-in tools. Edits happen directly
  in the worktree; the source/default branch is not modified.

Test client/workflow:
  Collects changed file bytes from Git and validates repository confinement, then
  publishes the review branch. A human reviews it; the workflow does not merge.

Note: the worktree is a starting directory, not an OS sandbox. SDK tools such as
shell commands may access other resources available to the service identity.
```

## Run the example

Run from the `Code` directory with the API/workflows already running. Configure
`COLLABORATOR_PRODUCT_REPOSITORY_URL` with your actual source (or reuse a product
with a configured source). Configure enough enabled developer profiles for the
default three reviewers, or set `--reviewer-count` to match your intended group.
The CLI does not inherit repository/reviewer arguments from F5 profiles.

```powershell
dotnet run --project src\Collaborator.ApiClient -- --product demo-product --feature "Add CSV export for reports" --interactive
```

With `--interactive`, the client prompts for the human decisions shown above.
For automated testing, `--auto` simulates approvals of the specification,
architecture, and plan after applying any supplied feedback. These are client
decisions, **not human approvals**. Scripted developer responses are also
simulated, for example `--review-response <developer-id>=revise:include an
export-size limit`.
Supply responses for every assigned developer; `--auto` only supplies BA,
architecture, and coordinator decisions. The scripted command below assumes
those developer responses are supplied separately through the API.

```powershell
dotnet run --project src\Collaborator.ApiClient -- --product demo-product --feature "Add CSV export for reports" --feedback "Include a maximum export size and a test for empty reports" --auto
```

## Invoice emailing test-client flow

Start the existing local Collaborator services, then select **Collaborator: API
test client (invoice emailing)** in VS Code's Run and Debug menu and press F5.
This launch configuration is in [launch.json](../.vscode/launch.json).
It uses the existing client and workflow, not a separate test runner.

The profile targets the local Git remote at
`H:\src\collaborator-sample-app-remote.git`, matching the original test-client
profile. That repository must already exist; change `--repository-url` to your
actual invoice repository if needed. HTTPS, SSH, and local `file://` URLs are
supported; private remote sources need Git credentials configured on the workflow
host. Set `--base-branch` to select the main development line, or leave it unset
to use the repository's default branch. The environment equivalents are
`COLLABORATOR_PRODUCT_REPOSITORY_URL` and `COLLABORATOR_PRODUCT_BASE_BRANCH`;
explicit launch arguments override environment values. Each run pins the selected
branch's commit, and review-branch publication does not modify that base branch.
This flow does not create or reset the
sample repository. The API key is resolved through the client's normal
environment/user-secrets configuration.

The flow registers or reuses product `invoice-emailing-sample`, configures an
invoice email reviewer, and submits a prewritten feature request to:

- Email one selected invoice to one validated recipient on explicit request.
- Include invoice details in plain text and attach the existing CSV export.
- Add an injectable email transport and an externally configured SMTP adapter.
- Test with a fake transport: no real email, credentials, or SMTP service needed
  for automated tests.
- Cover validation, message and attachment contents, send count, transport
  failures, and preservation of existing CSV behavior.
- Document usage and configuration, adding a minimal build/test harness if the
  sample repository has none.

The client remains interactive: review and approve or revise the specification,
architecture, developer reviews, and implementation plan. It requests one
reviewer; selection follows the normal workflow's reviewer assignment rules, so
another enabled reviewer may be selected if other profiles exist. Each workflow
transition has a 15-minute wait limit, with the normal progress output enabled.

After approvals, the workflow implements the feature and publishes a review
branch without merging. The implementer can run builds and tests through its
SDK tools, but publication does not independently require passing build/test
results. Review that branch, run its tests, and configure a local mail catcher before
trying actual delivery. Running this client alone does not send invoices.

### Scripted invoice workflow

For a simulated-approval run, execute the following from the repository root
after building the client and starting the services. This reuses the launch
profile's feature request without changing its interactive F5 behavior:

```powershell
$profile = (Get-Content .vscode\launch.json -Raw | ConvertFrom-Json).configurations |
    Where-Object name -eq 'Collaborator: API test client (invoice emailing)'
$clientArgs = @($profile.args | Where-Object { $_ -ne '--interactive' }) +
    @('--auto', '--review-response', 'invoice-email-reviewer=approve')
dotnet Code\src\Collaborator.ApiClient\bin\Debug\net10.0\collab-client.dll @clientArgs
```

`--auto` simulates specification, architecture, and coordinator approvals, but
developer reviews still require explicit `--review-response` arguments. If a
different reviewer is assigned, resume the printed run ID with
`--run <id> --auto --review-response <assigned-developer-id>=approve` rather
than submitting another feature. These are simulated approvals, not human
reviews.

Implementation has a ten-minute server-side deadline; the profile's
`--timeout 900` controls how long the client waits for each transition, not
the server's SDK deadline. Analysis stages retain their existing deadlines.

### Finding the generated code for review

Successful client output ends with **Review generated code**, including in
`--quiet` mode. This handoff identifies the run's captured repository URL, review
branch, generated commit, base commit, and changed files. It provides PowerShell
commands to clone into a new absolute local folder, check the expected commit,
view the diff, and open the folder in VS Code. The folder is a suggested
destination, not a checkout already created by the client. Choose an unused
destination and stop if cloning fails or HEAD does not match the printed commit.

The implementation's temporary worktree is removed after generation. The
published Git branch is the persistent result; it is not merged into the
default branch or automatically checked out in your original sample application.
You can recover the handoff later without generating new code:

```powershell
dotnet Code\src\Collaborator.ApiClient\bin\Debug\net10.0\collab-client.dll --run <run-id> --quiet
```

Restart/update both the API and client when deploying this output change, so
resumed runs include their captured repository URL. Publication success is not
proof of build/test success; run the generated repository's documented checks
before merging.
